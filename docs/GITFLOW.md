# Git-флоу проекта

Правила работы с ветками, Pull Request и коммитами для всей команды и AI-агентов.
Цель — чтобы `main` всегда был стабильным (то, что реально показываем на защите),
а вся текущая разработка и её согласование происходили через `dev`.

> **Обязательное правило для разработчиков и AI-агентов:** все сообщения Git-коммитов
> **должны быть написаны на английском языке**. Это относится к заголовкам, телу коммита,
> squash-коммитам, merge-коммитам и revert-коммитам. Заголовки Pull Request также
> должны быть на английском. Язык задачи, общения или документации на это правило
> не влияет: даже если задача поставлена на русском, сообщение коммита пишется
> **только на английском**. Не использовать кириллицу в сообщениях коммитов и
> заголовках PR.

## Структура веток

```
main                    # только стабильные, согласованные версии (для защиты/демо)
 └── dev                # основная ветка разработки — сюда мёржатся все рабочие ветки
      ├── feature/...   # новая функциональность
      ├── fix/...       # исправление багов
      ├── refactor/...  # рефакторинг без изменения поведения
      ├── docs/...      # документация
      ├── chore/...     # рутина: конфиги, зависимости, CI, инфраструктура
      └── test/...      # тесты
```

- **`main`** — защищённая ветка. Обновляется **только** через PR из `dev`, и только когда
  функциональность в `dev` проверена и согласована командой. Никаких прямых коммитов
  и прямых PR из `feature/*`/`fix/*` в `main`.
- **`dev`** — основная ветка интеграции. Все рабочие ветки создаются от неё и мёржатся
  обратно в неё через Pull Request.
- **Рабочие ветки** (`feature/*`, `fix/*`, `refactor/*`, `docs/*`, `chore/*`, `test/*`) —
  создаются от актуального `dev`, живут ровно до мёржа своего PR, после мержа — удаляются.

## Соглашение об именах веток

Формат: `<slug>/<short-kebab-case-description>`

| Slug | Когда использовать |
|---|---|
| `feature/` | новая функциональность (эндпоинт, экран, алгоритм и т.п.) |
| `fix/` | исправление бага в уже существующем функционале |
| `refactor/` | изменение структуры/качества кода без изменения поведения |
| `docs/` | только документация (README, схемы, конспекты) |
| `chore/` | инфраструктура, зависимости, конфиги, CI/CD, не относящееся к коду фич |
| `test/` | добавление/правка тестов без изменения продуктового кода |

Название после slug — короткое, **на английском**, через дефис, отражает суть задачи,
без номеров задач «на всякий случай» (если есть таск-трекер — можно добавить номер в конец).

Примеры:

```
feature/route-optimization-graph
feature/dispatcher-planning-screen
fix/timezone-offset-in-time-window
refactor/split-optimizer-service
docs/gitflow
chore/setup-infra-repo
test/schedule-conflict-cases
```

## Рабочий процесс

1. Обновить локальный `dev`:
   ```bash
   git checkout dev
   git pull origin dev
   ```
2. Создать рабочую ветку от `dev`:
   ```bash
   git checkout -b feature/route-optimization-graph
   ```
3. Коммитить небольшими логическими шагами, **используя только английские сообщения**
   (см. правила коммитов ниже).
4. Периодически подтягивать актуальный `dev` в свою ветку, чтобы не копить конфликты:
   ```bash
   git fetch origin
   git rebase origin/dev
   ```
   (или `git merge origin/dev`, если rebase неудобен команде — главное придерживаться
   одного способа).
5. Запушить ветку и открыть **Pull Request в `dev`** (не в `main`).
6. PR проходит ревью минимум одним участником команды, обсуждаются комментарии,
   вносятся правки.
7. После согласования — мёрж в `dev`, ветка удаляется.
8. Когда в `dev` накопился согласованный, проверенный руками функционал (например,
   перед очередным контрольным показом или защитой) — отдельным осознанным действием
   командой делается **Pull Request из `dev` в `main`**. Это отдельный шаг, не
   автоматический, и решение о нём принимается совместно.

## Правила Pull Request

- Один PR — одна логическая задача. Не смешивать фичу и рефакторинг в одном PR,
  если можно разделить.
- **Заголовок PR — только на английском**, в стиле Conventional Commits, например:
  `feat(optimizer): add route generation with time windows`.
- В описании PR — что сделано и как проверить (какие сценарии прогнать вручную).
  Описание PR может быть на языке команды; это не отменяет требования к английскому
  заголовку PR и сообщениям коммитов.
- PR должен быть замёржен только после того, как хотя бы один человек из команды
  его посмотрел (ревью может быть кратким, но должно быть).
- Мёрж в `dev` — предпочтительно **squash merge** (один чистый коммит на фичу в
  истории `dev`) либо обычный merge commit — команда выбирает единый способ и
  придерживается его для всех PR.
- При squash merge **проверить итоговый заголовок и тело коммита**: они тоже должны
  быть на английском, даже если GitHub предлагает текст автоматически.

## Коммиты — Conventional Commits на английском

**Все сообщения коммитов, включая заголовок и тело, пишутся только на английском.**
Это строгое правило и для ручных коммитов, и для AI-агентов, независимо от языка запроса.

Формат заголовка коммита:

```
<type>(<scope>): <short description in English>
```

Если scope не нужен, допускается формат:

```
<type>: <short description in English>
```

- **Тип** — стандартный английский идентификатор Conventional Commits:
  - `feat` — новая функциональность
  - `fix` — исправление бага
  - `refactor` — рефакторинг без изменения поведения
  - `docs` — документация
  - `test` — тесты
  - `chore` — рутина/конфиги/зависимости/инфраструктура
  - `style` — форматирование, не влияющее на логику (отступы, пробелы, линтер)
  - `perf` — изменения, направленные на производительность
  - `build` — сборка, Docker, CI-пайплайны
  - `revert` — откат предыдущего коммита
- **Область** (`scope`) — необязательна, но желательна: имя модуля/сервиса, к которому
  относится изменение (`optimizer`, `api`, `planning-ui`, `db` и т.п.).
- **Описание** (`description`) — **на английском**, кратко и конкретно, в повелительном
  наклонении (imperative mood), с маленькой буквы, без точки в конце. Использовать
  глаголы `add`, `fix`, `update`, `remove`, `extract`, `improve`, `handle`, `prevent`
  вместо русского текста или форм `added`, `fixed`, `updates`.
  - хорошо: `fix(api): validate request time windows`
  - плохо: `fix(api): добавляет валидацию временного окна`
  - плохо: `fix(api): Fixed validation.`

### Примеры правильных коммитов

```
feat(optimizer): add balanced workload distribution mode
fix(planning-ui): handle empty request lists when comparing plans
refactor(api): extract plan comparison logic into a separate service
docs: document project git workflow
chore(infra): add Redis to infrastructure docker-compose
test(optimizer): add overlapping time window test cases
perf(optimizer): reduce route calculation time
build(ci): update Docker build workflow
```

### Тело коммита (по необходимости)

Если изменение не тривиальное — после заголовка через пустую строку добавляется тело
**на английском** с объяснением **почему** сделано именно так (не «что», это видно
из диффа). Пример:

```
fix(optimizer): reserve only the required duration for emergency jobs

Previously, the algorithm treated the entire request window (00:01–23:59)
as unavailable time for an engineer. As a result, one emergency request
could block the engineer's whole day.

Reserve only the actual 100-minute service duration so the remaining time
can be used for other requests.
```

### Обязательные инструкции для AI-агентов

При создании коммитов, PR и merge/squash-коммитов агент **должен**:

1. Следовать правилам веток и Pull Request из этого документа.
2. Составлять **все commit messages полностью на английском**, даже когда задача,
   переписка с пользователем, документация или кодовые комментарии написаны на русском.
3. Использовать формат Conventional Commits и английское описание в imperative mood.
4. Перед `git commit`, `git commit -m`, созданием коммита через API или squash merge
   проверять, что заголовок и тело сообщения написаны на английском и не содержат
   кириллицы. Если содержат — переписать на английском **до создания коммита**.
5. Использовать английский для заголовков PR, включая PR `dev → main`.
6. Не подставлять исходную русскую формулировку задачи в сообщение коммита.
7. Если изменения логически не связаны — разбивать их на отдельные коммиты.
8. Не делать прямые коммиты в `dev` или `main`: использовать рабочую ветку и PR.

### Что нельзя

- Сообщения коммитов на русском или смесь русского и английского.
- Коммиты вида `wip`, `fix`, `правки`, `ещё немного` — без корректного типа
  и описания сути на английском.
- Смешивание в одном коммите несвязанных изменений (например, фича + правка
  в Docker) — разбивать на отдельные коммиты.
- Коммиты напрямую в `main` или `dev`, минуя PR.

## Теги и релизы (опционально)

Если понадобится зафиксировать версию для сдачи (промежуточная/финальная), после
мёржа `dev → main` ставится тег с **английским** сообщением:

```bash
git tag -a v0.1.0 -m "Interim release"
git push origin v0.1.0
```
