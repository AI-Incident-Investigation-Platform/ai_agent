# 02. Overview — Service Observability

**Figma:** [B / Overview — Operational overview](https://www.figma.com/design/JFUcynM2y9vIq6vJ7efTOc?node-id=6-24)  
**Маршрут (предложение):** `/overview`  
**Приоритет:** P0  
**Пользователи:** Admin / Developer / Viewer с доступом к проекту.

## 1. Роль экрана

Первый экран после входа. За 5–10 секунд показывает, есть ли у выбранного проекта/окружения проблемы, какие из них критичны, какие расследуются и куда пользователю перейти дальше. Это **операционная стартовая страница**, а не маркетинговая аналитическая панель.

В макете основной заголовок — `Service observability`, подзаголовок — `Telemetry health and active incidents across connected systems`. Sidebar и шапка из `01_DESIGN_SYSTEM_AND_APP_SHELL.md`.

## 2. Композиция desktop

Верхняя область — четыре однотипные KPI-панели, ниже — два блока: слева широкая таблица `Recent incidents`, справа `Services requiring attention`. Desktop frame 1440×940; контентная зона от ~244 px до ~1418 px, отдельные панели с тёмно-синим фоном `panel/bg`, тонким бордером и небольшими радиусами. Значения KPI крупнее подписей; проблемы визуально выделяются цветными статусами, но не «покрашены» целиком.

### 2.1. Метрики / KPI

| Карточка в Figma | Значение в макете (демо) | Откуда данные | Поведение |
|---|---|---|---|
| `ACTIVE INCIDENTS` | `12` | Backend Incident Management | Переход в Incidents с фильтром незавершённых |
| `INVESTIGATING` | `03` | Backend Investigation Management | Переход в Live investigations с running |
| `P95 LATENCY` | `892 ms` | Агрегированная метрика при наличии источника | Переход к Metrics соответствующего проекта |
| `HEALTHY SERVICES` | `17 / 20` | Каталог сервисов + согласованные health indicators | Переход к Service map |

Второй мелкий текст в карточке — контекст (`2 critical`, `1 agent running`, `+183ms / 1h`, `3 require attention`). Не изображать динамику или `0`, если за нужный период данные не получены: показывать `—`, `No data` или `Source unavailable`.

**Примечание по MVP:** первые две карточки обязательны; latency/healthy-services показываем, когда есть данные и серверная агрегация. Для этого не нужно вычислять p95 по нескольким несопоставимым клиентским метрикам во Frontend.

### 2.2. Таблица Recent incidents

На макете пять строк: `INC-1042`, `INC-1041`, `INC-1040`, `INC-1039`, `INC-1038` (это фиктивные demo cases). Колонки:

- Incident (ID, при необходимости title в одной или двух строках).
- Service (основной затронутый сервис).
- Severity (`Critical`, `High`, `Medium`, `Low`).
- Incident status (`Open`, `Investigating`, `Awaiting Review`, `Resolved`).
- Detected (время с корректной timezone).

Таблица сортируется по времени обнаружения, новые сверху. Максимум 5–8 последних строк на Overview, полная выдача находится в `/incidents`. Клик по строке открывает `/incidents/:id`. Заголовок/ссылка `View all incidents` открывает реестр.

### 2.3. Services requiring attention

Компактный список проблемных сервисов с симптомом/метрикой и статусом. В макете три примера: `payment-service` (5xx), `order-service` (latency), `review-service` (consumer lag). Порядок: наиболее критичные сверху, при равенстве — по свежести события. Клик: открытие сервисной карточки в Service map либо отфильтрованный список инцидентов этого сервиса — в зависимости от готовности Service map.

Список не должен самостоятельно вычислять первопричину. Ошибка 500 — **симптом**, а не Root Cause.

## 3. Действия пользователя

1. Выбрать проект и окружение в общей шапке — все блоки загружаются заново для выбранного контекста.
2. Нажать на KPI — перейти к отфильтрованным данным.
3. Нажать строку инцидента — открыть подробную страницу и, если расследование идёт, соответствующую вкладку.
4. Открыть `Services requiring attention` — посмотреть проблему сервиса.
5. Запустить ручное расследование из глобального UI **только после согласования Backend flow**, у Developer/Admin. Не создавать ложную кнопку с неработающим действием.

## 4. Данные, необходимые от Backend

**Возможности, не окончательные эндпоинты:**

- Агрегированная сводка по текущему Project/Environment с временным диапазоном и временем обновления.
- Счётчики активных инцидентов, критичности и запущенных AI-расследований.
- Список последних инцидентов (`id`, `title`, `service`, `severity`, `incidentStatus`, `occurredAt`).
- Список проблемных сервисов (`serviceId`, `displayName`, `indicator`, `severity`, `lastSeen`).
- Метрики latency/health только при наличии официальной серверной семантики и источника.
- Индикация частичной недоступности телеметрии (`sourceStatus`, `freshness`) — желательно.

Для realtime достаточно получать notification `incident.created/status.changed` и `investigation.status.changed` и обновлять соответствующие REST-снимки; не требуется передавать все метрики через WebSocket.

## 5. Состояния

- **Loading:** скелетоны KPI + строк таблицы, layout не прыгает.
- **Пустой проект:** «Нет зарегистрированных сервисов/инцидентов» + понятный переход в Integrations/Projects, если права позволяют.
- **Ноль открытых инцидентов:** спокойный success-state, не выдумывать зеленую историю успешных расследований.
- **Нет метрик:** KPI с `No telemetry` и объяснением, остальные KPI продолжают работать.
- **Частичная ошибка:** упавшую панель можно повторно загрузить, остальные доступны.
- **Нет прав:** карточки и ссылки не показывают чужие проекты.
- **Устаревшие данные:** отображать `Last updated`, не показывать «live», когда соединение потеряно.

## 6. Нефункциональные требования

KPI не должны пересчитываться из десятков страниц инцидентов на клиенте. Тяжёлые запросы агрегирует Backend. При частых событиях WebSocket использовать дебаунс invalidation, чтобы UI не отправлял по 20 параллельных GET. На мобильном KPI в 1–2 колонки, таблица в компактном виде или горизонтальном локальном скролле.

## 7. Критерии приёмки

- [ ] Все четыре KPI имеют корректное значение или явное `No data`.
- [ ] Статусы Incident и Agent Run не смешаны.
- [ ] Таблица открывает точный Incident Detail.
- [ ] Список сервисов привязан к реальному Project/Environment.
- [ ] Новые инциденты доступны без ручной перезагрузки.
- [ ] Реализованы loading/empty/partial error и отсутствуют фиктивные production-метрики.
- [ ] Нет круговой диаграммы `Incidents by Severity`.
