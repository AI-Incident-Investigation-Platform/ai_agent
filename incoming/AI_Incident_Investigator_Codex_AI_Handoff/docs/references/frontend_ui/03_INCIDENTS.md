# 03. Incidents — Реестр инцидентов

**Figma:** [B / Incidents — Incident registry](https://www.figma.com/design/JFUcynM2y9vIq6vJ7efTOc?node-id=6-26)  
**Маршрут (предложение):** `/incidents`  
**Приоритет:** P0  
**Роли:** просмотр — Admin/Developer/Viewer; создание ручного investigation — Admin/Developer.

## 1. Назначение

Основной searchable-реестр всех зарегистрированных инцидентов в доступных пользователю проектах и окружениях. Отвечает на вопросы: что случилось, когда, на каком сервисе, насколько критично, в каком состоянии и можно ли открыть расследование.

## 2. Точная композиция Figma

Под стандартным App Shell: заголовок `Incidents`, описание `Search, filter and review incident history across connected projects`. Справа в шапке кнопка `+ New investigation` (разрешённые роли). Ниже — отдельная горизонтальная панель фильтров (~80 px высотой), ещё ниже широкая таблица `ALL INCIDENTS`, под ней пагинация.

### 2.1. Верхняя панель фильтров

В Figma поля: `Search by ID or service`, `All severities`, `All statuses`, `All projects`, `Last 30 days`. В реальной версии учесть ещё `Environment` и, желательно, `Service` — их можно вынести в расширенные фильтры, не ломая исходную плотную композицию.

- Поиск: ID, title, service name; debounced 250–400 мс, Enter — немедленно.
- Severity: Multi/Single filter по `Critical`, `High`, `Medium`, `Low` (вариант выбора согласовать, но модель должна поддержать несколько фильтров).
- Status: `Open`, `Investigating`, `Awaiting Review`, `Resolved`.
- Project/Environment: значения только из разрешённых пользователю.
- Дата: предустановки 24h/7d/30d + произвольный диапазон после MVP.
- `Reset filters`, «clear search», сохранение применённых параметров в URL query string. Фильтрация должна быть **серверной**, не по текущей странице результатов.

### 2.2. Таблица инцидентов

Визуально одна большая панель с заголовком `ALL INCIDENTS`, количеством записей и столбцами:

| Колонка | Смысл и правила |
|---|---|
| ID / Title | `INC-1042 Checkout failing`, краткий заголовок, ссылка на детали |
| Service | Основной затронутый сервис; для нескольких — основной + `+N` |
| Severity | Цветной, подписанный статус |
| Status | Только статус **инцидента**, не AI Run |
| Detected | Время первого обнаружения, human-readable + tooltip с полным ISO timestamp |

В MVP необходимо также поддержать фильтр по проекту, окружению и период времени, даже если эти столбцы не всегда видны. Сортировка по `Detected` (по умолчанию новые сверху), severity и статусу — при поддержке API. Строка целиком интерактивна, доступна с клавиатуры, имеет hover/focus и не содержит вложенных кнопок с конфликтующим кликом.

Постраничная загрузка: 20/50 строк, prev/next, общее количество, отсутствие скачков страниц при новых событиях. Не изобретать infinite scroll вместо понятной пагинации.

### 2.3. Кнопка New Investigation

Открывает понятную форму/диалог: Project, Environment, Service (если известен), описание/тип проблемы, временной диапазон и `Start`. Поля/валидация должны соответствовать будущему контракту Backend. При успехе открыть созданный Incident Detail/Run. При `403` скрыть кнопку для Viewer, при ошибке не показывать ложный запуск.

Если API ручного запуска пока не готов, кнопка в mock-прототипе визуально присутствует, но в production не должна притворяться работающей: лучше feature flag/disabled с объяснением.

## 3. Пользовательские сценарии

1. Поиск `payment` → отображаются только соответствующие инциденты из всех разрешённых проектов.
2. Severity `Critical` + Status `Investigating` → таблица и счётчик обновляются, пагинация сбрасывается на 1.
3. Открыть `INC-1042` → `/incidents/INC-1042` (реальный `id` из Backend).
4. Вернуться назад → состояние фильтров, сортировки и страницы восстанавливается из URL.
5. Поступил новый alert → запись становится доступной; если пользователь на странице 4, не переставлять ему таблицу неожиданно. Показать `New incidents available`, позволить обновить.

## 4. Слой данных

**Требуется от Backend (без фиксации окончательного REST path):**

- `listIncidents({projectId, environment, serviceId, query, severities, statuses, from, to, sort, page, pageSize})`.
- Ответ с массивом incident summaries, `totalCount`/cursor или page metadata, server time.
- Сведения о доступных проектах, окружениях и сервисах для фильтров.
- `createInvestigation` / manual incident start, если согласовано.
- Реакция на серверные события о новом инциденте/смене статуса: refresh или аккуратное обновление кеша.

Рекомендуемый UI view model: `{id, title, project, environment, affectedServices[], severity, incidentStatus, occurredAt, updatedAt, currentInvestigationId?}`. Это **эскиз frontend-модели**, а не утверждённый Backend DTO.

## 5. Состояния и ошибки

- Initial loading: skeleton для таблицы и полей.
- Empty registry: нет инцидентов в выбранном проекте — спокойное сообщение, не красная ошибка.
- No matches: комбинация фильтров не нашла записей → `Clear filters`.
- Network error: не стирать уже загруженные данные мгновенно; пометить stale, предложить retry.
- `401`/`403`: перезайти либо permission denied, без утечек.
- Инцидент удалён/недоступен: кликом по старой строке перейти в `404/403` Incident Detail.
- Загрузка нового списка отменяет устаревший запрос (race control), чтобы результаты фильтров не перемешались.

## 6. Критерии приёмки

- [ ] Поиск, фильтры, серверная сортировка и пагинация работают вместе.
- [ ] Параметры фильтров сохраняются в URL.
- [ ] Статусы `Open/Investigating/Awaiting Review/Resolved` отображаются корректно.
- [ ] Click row → нужная страница инцидента.
- [ ] Реaltime изменения не сбрасывают фильтры и позицию пользователя.
- [ ] Viewer не может запустить investigation.
- [ ] Отсутствуют искусственные/случайные данные в реальном режиме.
