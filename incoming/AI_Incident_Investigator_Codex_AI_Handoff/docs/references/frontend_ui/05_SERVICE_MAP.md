# 05. Service Map — Карта микросервисов и зависимостей

**Figma:** [B / Service map — Service topology](https://www.figma.com/design/JFUcynM2y9vIq6vJ7efTOc?node-id=6-30)  
**Маршрут (предложение):** `/service-map`  
**Приоритет:** P1 — графовая визуализация; базовый каталог сервисов нужен для проекта и интеграций в P0.  
**Роли:** доступ на чтение в рамках разрешённого проекта у Admin/Developer/Viewer.

## 1. Задача

Показать архитектурное окружение выбранного проекта: какие сервисы участвуют в обработке запросов, какие связи между ними подтверждены данными, какие сервисы испытывают проблемы и какой из них выбран пользователем. Эта страница — **визуальная навигация по состоянию системы**, а не отдельный AI Agent и не автоматическая доказательная причинно-следственная модель.

## 2. Что отражает макет Figma

Заголовок `Service map`, подпись `Read-only topology inferred from configured service metadata and traces`. Вверху `Last 24 hours`. Основной блок `SERVICE DEPENDENCY MAP` с шестиэлементной топологией демо E-commerce, справа более узкая боковая панель `SERVICE DETAILS`.

На карте в прототипе:

```text
                 API gateway
               /      |      \
        user-service order-service review-service
                              |
                payment-service — inventory-service
```

Это **иллюстративная** топология демонстрационного приложения, её нельзя безусловно считать истинной: реальные связи должны поступать из настроенного каталога сервисов/реальных traces. Межсервисную причинность нельзя выводить только из геометрии нарисованных линий.

Карточка сервиса: name, компактный health state (`Healthy`, `Degraded`, `Critical`, `Unknown`), status dot. Линии без стрелок в исходном макете; в реализации можно добавить стрелки направления вызова, **только когда оно достоверно известно**. Элементы располагаются на графовом холсте, а не в таблице; панель справа обновляется при выборе узла.

### Правая панель Service Details

Для `payment-service` в макете показано:

- Название сервиса, статус `CRITICAL`.
- Error rate 12.8%.
- p95 latency 1.48s.
- Restarts / 24h = 02.
- Dependencies = 4.
- Open incidents = 1.

В production каждое поле из авторитетного источника/агрегации; при отсутствии метрики — `No data`, а не 0. Ссылка на текущие инциденты данного сервиса, прямые переходы в Logs & Metrics / Traces при наличии исходных идентификаторов.

## 3. UX-поведение

1. Выбрать Project + Environment → загрузить карту и доступные status indicators.
2. Нажать service node → визуально выделить узел, показать Service Details.
3. Нажать связанный incident → открыть Incident Detail.
4. Нажать `View logs / View metrics / View traces` → открыть соответствующую страницу с сохранением service/time context.
5. Изменить time range → обновить **только** зависимые от периода графовые факты и метрики. Не путать с постоянной регистрацией сервиса.
6. Для P1: pan/zoom/fit-to-screen, фокусировка с клавиатуры, легенда связей (Observed / Configured / Unknown), ограничение числа узлов/кластеризация.

### Чего не должно быть

- Произвольно добавленных «умных» стрелок и auto-discovery, которого реально нет в API.
- Раскрашивания целого пути как «Root Cause», если это не подтверждённая RCA причинная цепочка.
- Неограниченного графа из тысяч элементов, блокирующего браузер.
- Действий `restart`, `scale`, `kill container` — наш агент read-only.

## 4. Источники и нужные данные

До окончательных контрактов ожидаются следующие **возможности Backend**:

- Список зарегистрированных сервисов проекта/окружения с `id`, `name`, `metadata`, `healthStatus`.
- Список подтверждённых связей `sourceServiceId`, `targetServiceId`, `relationKind`, `observedAt`, `sourceRef`.
- Агрегированные сервисные метрики (error/latency/restarts) с временем актуальности и единицами.
- Счётчики связанных инцидентов и переходы по `serviceId`.

Возможные источники: OpenTelemetry/Tempo по `service.name` и spans; конфигурация Project→Environment→Service; Prometheus; Docker diagnostic adapter. Это *требование к подготовке данных*, не подтверждение существования готового topology API.

### Режим без topology API

Если есть только список сервисов без достоверных связей, показывать **карточки каталога сервисов** с состоянием и текстом `Dependency relationships unavailable`. Не соединять узлы случайными линиями ради похожести на макет.

## 5. Визуальные детали

- Область графа — самая большая панель (~889×620 в Figma), детали — справа (~270×620).
- Фон/границы — общая `SRE / Dark UI`, карточки узлов немного светлее основного фона; статус обозначается точкой и подписью.
- Линии тонкие и малоконтрастные, не перекрывают надписи узлов.
- Hover подсвечивает связи, выбранный узел сохраняет selection state; network errors не перерисовывают граф в пустой экран.
- На узком экране граф выше панели деталей, справа sidebar collapses.

## 6. Состояния

Loading; no services; unknown topology; partial telemetry; missing metrics; service disappeared; project forbidden; too many nodes; graph API unavailable; stale observations. Статусы могут изменяться через REST refresh/WebSocket notification, но по подписке клиент не должен производить тяжёлые запросы чаще заданного интервала.

## 7. Приёмка

- [ ] Карта или корректный fallback показывают сервисы текущего проекта/окружения.
- [ ] Связи строятся только из backend source, нет вымышленных edges.
- [ ] По клику узла открываются реальные Service Details и связанные incidents.
- [ ] Unknown/missing telemetry не заменяется на `Healthy`.
- [ ] Крупная карта остаётся управляемой, доступна в узком окне.
- [ ] P1 графовые возможности не блокируют основную функциональность MVP.
